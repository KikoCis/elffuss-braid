Elffuss Braid is version control for repositories where many AI coding agents land changes at the same time.

Elffuss Braid es un sistema de control de versiones para repositorios en los que muchos agentes de IA aterrizan cambios a la vez.

Written from scratch in Rust. Each agent commits in its own workspace, and a change that fell behind is rebased onto whatever landed first. Git stays at the edges, so GitHub keeps working.

Escrito desde cero en Rust. Cada agente hace commit en su propio espacio de trabajo, y si un cambio se ha quedado atrás, braid le hace rebase sobre lo que haya aterrizado antes. Git se queda en los bordes, así que GitHub sigue funcionando.

Three agents get three small tasks in the same repository. Two of them, A and B, are asked to reword the same line of notes.txt. The third, C, only adds a line at the end. They finish within moments of each other.

Tres agentes reciben tres encargos pequeños en el mismo repositorio. A dos de ellos, A y B, les toca reescribir la misma línea de notes.txt. El tercero, C, solo añade una línea al final. Terminan casi a la vez.

II

2. In git, they step on each otherEn git, se pisan

Put them in one checkout and they trip over its single index:

Si trabajan en la misma copia, chocan con el índice, porque solo hay uno:

So each one gets a clone of its own, and the fight moves to the push. C gets in first. A is turned away:

Así que cada uno se lleva su propio clon, y la pelea pasa al push. C llega primero. Al agente A le rechazan el suyo:

A fetches, rebases and pushes again. B is turned away too: its rebase runs into A's edit, it fixes the conflict and pushes again, and if anyone got in meanwhile, it is turned away once more. Every agent that loses the race runs the same lap: fetch, rebase, push, again. The more agents, the more laps; we counted them in Measured against git. And much of what comes back is text written for people.

A hace fetch, rebase y vuelve a hacer push. Con B pasa lo mismo, pero al hacer rebase choca con el cambio de A: arregla el conflicto, vuelve a empujar y, si alguien ha entrado entretanto, otra vez rechazado. Todo agente que pierde la carrera da la misma vuelta: fetch, rebase, push, y vuelta a empezar. Cuantos más agentes, más vueltas; las contamos en «Medido frente a git». Y buena parte de lo que devuelve git es texto pensado para personas.

III

3. The same three agents, in braidLos mismos tres, en braid

Braid gives each agent a workspace of its own over one shared store. There is no index to fight over and no staging area: an agent commits what it changed, and lands it. All three commit before anyone lands; then they land as they finish.

Braid da a cada agente su propio espacio de trabajo sobre un único almacén compartido. No hay índice por el que pelearse ni área de preparación: el agente hace commit de lo que ha cambiado y lo aterriza. Los tres hacen commit antes de que aterrice nadie, y luego aterrizan según van terminando.

C is first. Nothing has landed since it started, so its change goes straight in:

C es el primero. No ha aterrizado nada desde que empezó, así que su cambio entra directo:

A is one changeset behind. It does not fetch and it does not retry: in one short step, braid rebases A's change onto C's and merges the one file both touched.

A va un changeset por detrás. Ni hace fetch ni reintenta: en un solo paso corto, braid le hace rebase sobre el cambio de C y fusiona el único fichero que han tocado los dos.

B cambió la misma línea que A. Eso es un conflicto de verdad, y ahí ninguna herramienta debería ir a ciegas. Braid se para y deja main donde estaba:

Cada lado se nombra desde el punto de vista de B: base es el ancestro común, branch lo que tiene main ahora y workspace su propio cambio. Las líneas se cuentan desde 0 y el final del tramo no se incluye; next le dice qué ejecutar:

B runs braid update. Its copy gets the markers, with C's line already merged below them:

B ejecuta braid update. Su copia recibe las marcas de conflicto, con la línea de C ya fusionada debajo:

Until the markers are gone, braid status says why a commit would be refused:

Mientras queden marcas, braid status explica por qué no aceptaría el commit:

B writes one line that keeps both edits and commits without a new message, so the change keeps its own. Then it lands:

B escribe una línea que recoge las dos ediciones y hace commit sin mensaje nuevo, así que el cambio conserva el suyo. Después aterriza:

Start the three landings at the same moment and the order changes from run to run. The shape does not: one goes straight in, one is rebased, one gets the conflict.

Si lanzas los tres aterrizajes a la vez, el orden cambia de una ejecución a otra, pero la forma no: uno entra directo, a otro se le hace rebase y otro se lleva el conflicto.

Run it yourselfRepítela tú
bash
# with braid on your PATH (see Quick start)
export BRAID_AUTHOR="Ada Lovelace <ada@example.org>"
cd "$(mktemp -d)"
braid init repo
printf 'title\nalpha\nbeta\ngamma\n' > seed.txt
(cd repo && BRAID_AGENT=seeder braid change create --base none \
   --set notes.txt=@../seed.txt -m "Seed the notes" --land main)
for n in a b c; do (cd repo && braid workspace add $n ../$n); done
printf 'title\nalpha, from a\nbeta\ngamma\n'        > a/notes.txt
printf 'title\nalpha, from b\nbeta\ngamma\n'        > b/notes.txt
printf 'title\nalpha\nbeta\ngamma\ndelta, from c\n' > c/notes.txt
(cd a && BRAID_AGENT=agent-a braid commit -m "a: alpha")
(cd b && BRAID_AGENT=agent-b braid commit -m "b: alpha")
(cd c && BRAID_AGENT=agent-c braid commit -m "c: delta")
(cd c && BRAID_AGENT=agent-c braid land)     # fast-forward
(cd a && BRAID_AGENT=agent-a braid land)     # rebased, 1 path merged
(cd b && BRAID_AGENT=agent-b braid land)     # exit status 2: main did not move
(cd b && BRAID_AGENT=agent-b braid update)   # markers in b/notes.txt
printf 'title\nalpha, from a and b\nbeta\ngamma\ndelta, from c\n' > b/notes.txt
(cd b && BRAID_AGENT=agent-b braid commit)   # keeps its message
(cd b && BRAID_AGENT=agent-b braid land)     # fast-forward
(cd a && BRAID_AGENT=agent-a braid update)   # a gets the same file as b
(cd c && BRAID_AGENT=agent-c braid update)   # and so does c
(cd repo && braid op log -n 3)
(cd repo && braid blame main notes.txt)
git init --quiet --bare remote.git
(cd repo && braid git sync ../remote.git)

Today, braid git sync runs when you call it, and every changeset reaches git as a commit of its own. Automatic, curated sync is being built: agents keep landing in braid, and git receives a clean history to read and review. It is not released yet. This section will say how it works once it ships.

Hoy, braid git sync se ejecuta cuando lo lanzas, y cada changeset llega a git como un commit propio. Estamos construyendo una sincronización automática y curada: los agentes siguen aterrizando en braid y git recibe una historia limpia, lista para leer y revisar. How braid worksCómo funciona braid

  1. Everything is an immutable object named by its BLAKE3 hash: file contents, directories and changesets. Objects are never rewritten in place; the exact bytes are in docs/spec/format-v1.md, with golden vectors.
  2. A changeset records the files that changed against its first parent, plus the root tree it produces. History, blame and rebase read that short list, and the root id still commits to the whole repository.
  3. Agents commit in parallel, each in its own workspace. Landing is the one step they take in turn, and it is short: a fast-forward, or a rebase path by path that merges only the files both sides touched. Conflicts come back as data, and the branch does not move.
  4. Many processes share one store without a daemon. Segments are leased with locks the kernel releases if a process dies, objects reach the disk before anything that refers to them, and an append-only op log records every ref change, so braid undo can step back.
  5. The same API at every tier, so a local store, a per-machine daemon, a cache and a server all answer the same requests. The server has a first version, BraidHub; the caches and the daemon are planned (milestones 6 and 7).
  1. Todo es un objeto inmutable que se nombra por su hash BLAKE3: el contenido de los ficheros, los directorios y los changesets. Ningún objeto se reescribe en su sitio; los bytes exactos están en docs/spec/format-v1.md, con vectores de referencia.
  2. Un changeset registra los ficheros que cambiaron respecto a su primer padre, más el árbol raíz que resulta. La historia, blame y el rebase leen esa lista corta, y el id de la raíz sigue fijando el estado de todo el repositorio.
  3. Los agentes hacen commit en paralelo, cada uno en su propio espacio de trabajo. Aterrizar es el único paso que dan por turnos, y es corto: un fast-forward, o un rebase ruta a ruta que solo fusiona los ficheros que han tocado los dos lados. Los conflictos vuelven como datos, y la rama no se mueve.
  4. Muchos procesos comparten un almacén sin daemon. Los segmentos se reservan con cerrojos que el kernel libera si un proceso muere, los objetos llegan al disco antes que lo que apunta a ellos, y un registro de operaciones que solo crece apunta cada cambio de ref, para que braid undo pueda dar marcha atrás.
  5. La misma API en cada nivel, de modo que un almacén local, un daemon por máquina, una caché y un servidor respondan a las mismas peticiones. El servidor ya tiene una primera versión, BraidHub; las cachés y el daemon están previstos (fases 6 y 7).

Where the ideas come from: ScionDe dónde vienen las ideas: Scion

Braid starts from ideas Anthropic published about Scion, its internal source control system (Redesigning source control at Anthropic): changesets stored against the first parent, server-side merges, minimal branch state, immutable objects any cache can serve. Braid is an independent implementation: it contains no Anthropic code and is not affiliated with or endorsed by Anthropic. What braid takes from Scion, and where it differs.

Braid parte de ideas que Anthropic publicó sobre Scion, su sistema interno de control de versiones (Redesigning source control at Anthropic): changesets guardados respecto al primer padre, fusiones en el servidor, ramas con un estado mínimo y objetos inmutables que cualquier caché puede servir. Braid es una implementación independiente: no contiene código de Anthropic y no tiene relación con Anthropic ni cuenta con su respaldo. Qué toma braid de Scion y en qué se aparta.

Ask your agentPídeselo a tu agente

Braid comes with instructions written for coding agents. In a project that is a git repository, ask yours, whatever harness runs it:

Braid trae instrucciones escritas para agentes de programación. En un proyecto que sea un repositorio de git, pídeselo al tuyo, sea cual sea la herramienta con la que lo uses:

prompt
Install braid in this project and set it up for agents, following https://braid.elffuss.com/agents.md (read it whole, with curl -fsSL)
petición
Instala braid en este proyecto y configúralo para agentes siguiendo https://braid.elffuss.com/agents.md (léelo entero, con curl -fsSL)

Your agent installs braid with cargo, tells you what in the project braid does not run, such as git hooks, offers to make a git remote if the project has none, imports the project's git history, and writes the rules for agents into its AGENTS.md with braid agents init. From then on, every agent session works in a braid workspace of its own, where git refuses to run, lands through braid, and tells you when what it landed is waiting for a sync to the git remote. Git stays the source of truth, and in a clone where braid is not set up, agents work with git as before.

Tu agente instala braid con cargo, te avisa de lo que braid no ejecuta en el proyecto, como los hooks de git, se ofrece a crearle un remoto de git si no tiene ninguno, importa su historia de git y, con braid agents init, escribe en su AGENTS.md las reglas para los agentes. A partir de ahí, cada sesión trabaja en su propio espacio de trabajo, donde git se niega a funcionar, aterriza sus cambios con braid y te avisa cuando lo que ha aterrizado está pendiente de sincronizar con el remoto de git. Git sigue siendo la fuente de verdad, y en un clon donde braid no está configurado los agentes trabajan con git, como siempre.

By handA mano

The same steps, in a git checkout on its main branch with nothing to commit, where git has a user.name and a user.email:

Los mismos pasos, en una copia de git que esté en su rama principal, sin nada pendiente de commit y con user.name y user.email configurados en git:

bash
cargo install --locked --git https://github.com/KikoCis/elffuss-braid --tag v0.1.1 elffuss-braid-cli
braid init                       # .braid/: the store and the agents' workspaces
mkdir -p "$(git rev-parse --git-path info)"
echo .braid >> "$(git rev-parse --git-path info/exclude)"   # git ignores braid, in this checkout only
printf 'name = %s\nemail = %s\n' "$(git config user.name)" "$(git config user.email)" > .braid/config
braid git import .               # the project's whole history
touch CLAUDE.md                  # only if agents work here with Claude Code
braid agents init                # the rules for agents, into AGENTS.md
git add AGENTS.md CLAUDE.md      # leave CLAUDE.md out if there is none
git commit -m "Set up braid for agents"
braid git import .               # braid's main takes that commit

What it adds to your projectQué añade a tu proyecto

  1. AGENTS.md, which most coding agents read: a section between <!-- braid:start --> and <!-- braid:end --> with the rules every session follows. Running braid agents init again, after a braid upgrade for example, rewrites it in place and never touches the rest of the file.
  2. CLAUDE.md for Claude Code and GEMINI.md for Gemini CLI: the line @AGENTS.md, so that they read the same rules.
  3. These files are committed with git, so every clone and every new session has them. Nothing of braid's goes into git: .braid/ holds the store, the workspaces and .braid/config, the name and e-mail address that sign what agents land.
  1. AGENTS.md, que leen la mayoría de los agentes de programación: una sección entre <!-- braid:start --> y <!-- braid:end --> con las reglas que sigue cada sesión. Si vuelves a ejecutar braid agents init, por ejemplo tras actualizar braid, la reescribe en su sitio y nunca toca el resto del fichero.
  2. CLAUDE.md para Claude Code y GEMINI.md para Gemini CLI: la línea @AGENTS.md, para que lean las mismas reglas.
  3. Estos ficheros se guardan en git, así que los tienen cada clon y cada sesión nueva. Nada de braid entra en git: .braid/ guarda el almacén, los espacios de trabajo y .braid/config, con el nombre y el correo que firman lo que aterrizan los agentes.

The rules, in short: they apply only where the checkout has a .braid directory, so a fresh clone or CI works with git as before; never edit files or use git in the project root, your shared checkout; each session works in a workspace of its own under .braid/work/, and commits and lands with braid; on a conflict (exit status 2), braid update, fix the markers, commit and land again; braid update before a new task; and at the end, the session tells you and offers braid git sync to the git remote.

Las reglas, en resumen: solo valen donde la copia tiene un directorio .braid, así que un clon nuevo o la integración continua siguen con git; nada de editar ficheros ni usar git en la raíz del proyecto, que es tu copia compartida; cada sesión trabaja en su propio espacio de trabajo, dentro de .braid/work/, y registra y aterriza sus cambios con braid; ante un conflicto (código de salida 2), braid update, se arreglan los marcadores y se vuelve a registrar y aterrizar; braid update antes de cada tarea nueva; y al terminar, la sesión te avisa y te ofrece braid git sync hacia el remoto de git.

The instructions are agents.md, part 1 of the repository's AGENTS.md; there is an llms.txt too. agents.md also says what to check before setting braid up, and what to do when a step fails. Quick start, just below, tries braid on its own repository.

Las instrucciones son agents.md, la primera parte del AGENTS.md del repositorio, en inglés; también hay un llms.txt. agents.md dice además qué comprobar antes de configurar braid y qué hacer si falla un paso. «Primeros pasos», justo debajo, prueba braid con su propio repositorio.

Quick startPrimeros pasos

Braid stores history, moves it in and out of git bit for bit, and gives each agent a workspace of its own. Build it, then import a git repository, this one for a start:

Braid guarda historia, la mete y la saca de git bit a bit, y da a cada agente su propio espacio de trabajo. Compílalo e importa un repositorio de git; para empezar, este mismo:

bash
git clone https://github.com/KikoCis/elffuss-braid
cd elffuss-braid
cargo build --release
export PATH="$PWD/target/release:$PATH"
SRC="$PWD"                       # this clone; another repository works too, with
                                 # its branch for main and one of its files for README.md

braid init /tmp/demo
cd /tmp/demo
braid git import "$SRC"          # every local branch and tag
braid log main -n 5
braid log main -- README.md      # only the changes to a path
braid blame main README.md       # who last changed each line
braid show main --json
braid fsck
braid stats        # objects by kind, and how they are stored: whole, deltas, chunks

Exporting writes the same commits back, with the same ids:

Al exportar se escriben los mismos commits, con los mismos ids:

bash
git init --bare /tmp/mirror.git
braid git export /tmp/mirror.git

Ids can be checked with any BLAKE3 implementation, for example the reference b3sum tool. In the clone, it prints the id that braid hash-object README.md gives:

Los ids se pueden comprobar con cualquier implementación de BLAKE3, por ejemplo la herramienta de referencia b3sum. En el clon, imprime el mismo id que da braid hash-object README.md:

bash
cd "$SRC"         # the clone, where README.md is
b3sum --derive-key "elffuss-braid 2026 blob v1" README.md

Many AI coding agents on one repositoryMuchos agentes de programación en un repositorio

Each agent gets its own workspace. There is no staging area and no shared index: an agent commits what it changed and lands it, and braid rebases it onto whatever the others landed first.

Cada agente tiene su propio espacio de trabajo. No hay área de preparación ni índice compartido: el agente hace commit de lo que ha cambiado y lo aterriza, y braid le hace rebase sobre lo que hayan aterrizado antes los demás.

bash
cd /tmp/demo                         # any braid repository
export BRAID_AUTHOR="Ada Lovelace <ada@example.org>"
export BRAID_AGENT=agent-1           # recorded with everything this agent does
braid workspace add agent-1          # .braid/work/agent-1, tracking main
cd .braid/work/agent-1
echo 'fn main() {}' > main.rs
braid status
braid commit -m "Add main.rs"
braid land                           # fast-forward, or a rebase onto main

Every change to a branch or ref (imports, landings, syncs) is in the op log, and braid undo steps back through them, newest first. Here it takes the landing back, and the changeset stays in the workspace, ready to land again:

Cada cambio de una rama o una ref (importaciones, aterrizajes, sincronizaciones) queda en el registro de operaciones, y braid undo los deshace uno a uno, del más reciente hacia atrás. Aquí deshace el aterrizaje, y el changeset sigue en el espacio de trabajo, listo para aterrizar otra vez:

bash
braid op log      # who did what, newest first
braid undo        # takes the landing back

What an agent can rely onCon qué puede contar un agente

  • IdentityIdentidad

    BRAID_AGENT is written into the op log and into every changeset the agent makes, and survives rebases; changesets imported from git name no agent. BRAID_AUTHOR signs the changesets the agent commits, or creates without a checkout, and the ones it remakes in a rebase. A merge made by git sync is signed instead with the agent label and the email in .braid/config, or <agent>@example.org.

    BRAID_AGENT queda escrito en el registro de operaciones y en cada changeset que crea el agente, y sobrevive a los rebases; los changesets importados de git no nombran agente. BRAID_AUTHOR firma los changesets que el agente crea, con commit o sin checkout, y los que rehace en un rebase. Una fusión hecha por git sync, en cambio, se firma con la etiqueta del agente y el correo de .braid/config, o con <agente>@example.org.

  • OutputSalida

    --json on every command; change create always prints JSON.

    --json en todos los comandos; change create imprime siempre JSON.

  • Exit statusCódigo de salida

    0 done, 1 failed, 2 conflicts (the branch did not move), or a command line braid could not parse; with --json, the outcome is conflicts only for a conflict. A failure is printed as text on standard error.

    0 hecho, 1 fallo, 2 conflictos (la rama no se movió) o un comando que braid no sabe interpretar; con --json, solo en un conflicto el outcome vale conflicts. Un fallo se imprime como texto en la salida de error.

  • StatusEstado

    braid status --json gives behind_by, unlanded, ready_to_commit and blocking, which lists the same reasons braid commit refuses with, a missing author among them.

    braid status --json da behind_by, unlanded, ready_to_commit y blocking, que lista los mismos motivos por los que braid commit se niega, entre ellos que no haya autor.

  • Secrets guardGuarda de secretos

    New .env*, *.pem and id_* files, and files over 1 MiB, wait for braid track. --force leaves them out.

    Los ficheros nuevos .env*, *.pem e id_*, y los de más de 1 MiB, esperan a braid track. --force los deja fuera.

  • Short idsIds cortos

    Six hex digits or more. An ambiguous one is an error that lists the candidates.

    Seis dígitos hexadecimales o más. Uno ambiguo es un error que lista los candidatos.

  • Conflict kindsTipos de conflicto

    CONTENT, MODIFY_DELETE, MODE, DF, DIR_REMOVED, CASE. braid resolve settles the ones that are not about content.

    CONTENT, MODIFY_DELETE, MODE, DF, DIR_REMOVED, CASE. braid resolve zanja los que no son de contenido.

  • Checkouts

    They never follow symlinks, and nothing from repository content is ever run. A workspace holds a .git file that points nowhere, so git inside one stops instead of acting on the checkout around it.

    Nunca siguen enlaces simbólicos, y nunca se ejecuta nada que venga del contenido del repositorio. Un espacio de trabajo lleva un fichero .git que no apunta a ninguna parte, así que git, dentro de él, se detiene en vez de actuar sobre el checkout que lo rodea.

  • No checkoutSin checkout

    braid change create makes a changeset without a working copy, and can land it. --expect takes the full blob id the agent read; a mismatch is refused.

    braid change create crea un changeset sin copia de trabajo, y puede aterrizarlo. --expect recibe el id completo del blob que el agente leyó; si no coincide, se rechaza.

Working with gitTrabajar con git

Repositories come in with their whole history, and git hosts keep working as mirrors.

Los repositorios entran con toda su historia, y los servidores de git siguen funcionando como espejos.

ImportImportarbraid git import

Goes through gitoxide and brings every local branch and tag; to bring every branch of a remote, import a git clone --mirror. Each commit is exported again as it is imported, and the import stops unless its id comes back the same. Running it again imports only what is new. A braid branch or tag follows git's only forward: when braid has work git does not have, or the two have diverged, it stays where it is, and the import lists it under kept with the reason. To keep a branch in step with a git remote, use git sync. Shallow and SHA-256 repositories are refused for now.

Pasa por gitoxide y trae todas las ramas locales y etiquetas; para traer todas las ramas de un remoto, importa un git clone --mirror. Cada commit se vuelve a exportar al importarlo, y la importación se detiene si su id no sale idéntico. Si se repite, solo importa lo nuevo. Una rama o etiqueta de braid solo sigue a la de git hacia delante: si braid tiene trabajo que git no tiene, o los dos han divergido, se queda donde está, y la importación la lista en kept con el motivo. Para mantener una rama al día con un remoto de git, usa git sync. Los clones superficiales y los repositorios SHA-256 se rechazan por ahora.

ExportExportarbraid git export

Writes braid refs, and everything they reach, into a git repository with the same ids. Changesets made in braid export deterministically, with their agent as a commit header. Git refs of the same names are overwritten, so export into a new repository; to keep an existing remote in step, use git sync.

Escribe las refs de braid, y todo lo que alcanzan, en un repositorio de git con los mismos ids. Los changesets hechos en braid se exportan de forma determinista, con su agente como cabecera del commit. Las refs de git con el mismo nombre se sobrescriben: exporta a un repositorio nuevo y, para mantener al día un remoto que ya existe, usa git sync.

SyncSincronizarbraid git sync
  • It fetches and imports the remote branch, then fast-forwards braid or pushes braid's branch, merging first when both moved.
  • The remote only ever fast-forwards: the push carries a lease on what was just fetched, and history there is never rewritten.
  • Conflicts move nothing and exit 2; a refused push exits 1.
  • --dry-run writes nothing, and --json names the outcome.
  • Hace fetch de la rama remota y la importa; después hace fast-forward en braid o push de la rama de braid, y antes fusiona si se han movido las dos.
  • El remoto solo avanza en fast-forward: el push lleva un lease sobre lo que se acaba de traer, y allí la historia nunca se reescribe.
  • Los conflictos no mueven nada y salen con 2; un push rechazado sale con 1.
  • --dry-run no escribe nada, y --json nombra el resultado.
braid git sync https://github.com/you/project.git --branch main
braid git sync https://github.com/you/project.git --dry-run --json

Braid contains no code from git (GPLv2). It reads and writes git data with gitoxide (MIT or Apache-2.0); git sync also runs the git binary as a subprocess, to set up its mirror, fetch and push.

Braid no contiene código de git (GPLv2). Lee y escribe datos de git con gitoxide (MIT o Apache-2.0); git sync además ejecuta el binario de git como subproceso, para preparar su espejo, hacer fetch y hacer push.

BraidHub: many machines, one mainBraidHub: muchas máquinas, un solo main

BraidHub is a braid server where repositories live. People and agents sign in with GitHub, and agents on any machine land on the same main, one after another, as they do on one machine.

BraidHub es un servidor de braid donde viven los repositorios. Personas y agentes entran con su cuenta de GitHub, y los agentes de cualquier máquina aterrizan en el mismo main, uno detrás de otro, igual que en una sola máquina.

Sign inEntrarbraid login

GitHub's device flow, run through the hub: braid prints a web address and a code; you open the address in any browser, enter the code and approve, so the agent's machine needs no browser of its own. The token is saved where only you can read it. braid hub whoami says who is signed in, and braid logout revokes the token on the hub.

Con el flujo de dispositivo de GitHub, a través del hub: braid muestra una dirección web y un código; abres la dirección en cualquier navegador, escribes el código y apruebas el acceso, así que la máquina del agente no necesita navegador. El token se guarda donde solo tú puedes leerlo. braid hub whoami dice quién ha entrado, y braid logout revoca el token en el hub.

PublishPublicarbraid hub publish
  • It creates the repository on the hub, uploads every branch and tag, and links your repository to it. On another machine, braid hub clone owner/name makes a linked copy.
  • A repository is private unless its owner makes it public.
  • With --mirror, a GitHub repository is kept as the mirror: every landing on the default branch is pushed there as a fast-forward, never a force push. The hub needs access to your GitHub repositories, granted once on its website.
  • If someone pushes to the mirror directly, the hub records it as diverged and goes on landing; the owner takes those commits in.
  • Crea el repositorio en el hub, sube todas las ramas y etiquetas, y enlaza con él tu repositorio. En otra máquina, braid hub clone dueño/nombre crea una copia enlazada.
  • Un repositorio es privado salvo que su dueño lo haga público.
  • Con --mirror, un repositorio de GitHub hace de espejo: cada aterrizaje en la rama por defecto se sube allí como fast-forward, nunca con un push forzado. El hub necesita acceso a tus repositorios de GitHub, que le das una vez en su web.
  • Si alguien hace push directamente al espejo, el hub lo registra como diverged y sigue aceptando aterrizajes; el dueño incorpora esos commits.
LandAterrizarbraid land

In a linked repository, it uploads what the hub lacks, lands there and moves the workspace onto the new head, with the same output and exit statuses as a local landing: a conflict exits 2, and main does not move. braid update brings in what agents on other machines landed, and braid hub status compares each branch with the hub's.

En un repositorio enlazado, sube lo que le falta al hub, aterriza allí y lleva el espacio de trabajo a la nueva cabeza; imprime lo mismo y sale con los mismos códigos que un aterrizaje local: ante un conflicto sale con 2, y main no se mueve. braid update trae lo que hayan aterrizado los agentes de otras máquinas, y braid hub status compara cada rama con la del hub.

AgentsAgentesbraid hub autopublish

Coding agents have their own guide, braidhub.elffuss.com/agents.md. They sign in once per machine, ask you once whether to publish the new projects they start, privately (braid hub autopublish on|off keeps your answer), and work from the hub from then on.

Los agentes de programación tienen su propia guía, en inglés: braidhub.elffuss.com/agents.md. Entran una vez en cada máquina, te preguntan una sola vez si deben publicar en privado los proyectos nuevos que empiecen (braid hub autopublish on|off guarda tu respuesta) y, desde entonces, trabajan desde el hub.

Measured against gitMedido frente a git

  • Ratios are braid / git for the same work on the same machine; below 1 means braid is faster or smaller.
  • braid and git run in alternating order, with warm caches, and the result is the median.
  • Each scenario checks both tools did the same work. A failed check is reported as an error, never as a number.
  • Git runs with its defaults, with automatic gc and maintenance turned off.
  • Only ratios and git's retry counts are published, never times or sizes, together with the script.
  • Not measured: cold caches, git's fsmonitor daemon or feature.manyFiles, and, for now, transfers between machines through BraidHub.
  • Cada ratio es braid / git para el mismo trabajo en la misma máquina; por debajo de 1, braid es más rápido o más pequeño.
  • braid y git se ejecutan en orden alterno, con las cachés calientes, y el resultado es la mediana.
  • Cada escenario comprueba que las dos herramientas hicieron el mismo trabajo. Una comprobación fallida sale como error, nunca como número.
  • Git se ejecuta con su configuración por defecto, con el gc y el mantenimiento automáticos desactivados.
  • Solo se publican ratios y los reintentos de git, nunca tiempos ni tamaños, junto con el script.

What is honest about thisSin letra pequeña

  • Version 0.1: keep git as the source of truth, and nothing only in braid.
  • Speed and size against git are in Measured against git, as ratios from one run of the script, with the commit measured: check them before relying on braid for speed.
  • BraidHub, which takes braid across machines, is a first version: for anything that matters, keep a GitHub mirror as the source of truth. There is no per-machine daemon, cache or virtual file system yet.
  • Nothing is ever removed from a store; there is no garbage collection yet.
  • Format v1 is frozen. Storage and protocols can still change, and an older braid refuses a newer store rather than guess.
  • Merges are textual: two changes can merge cleanly and still break the build.
  • log -- path and blame follow first parents and do not follow renames.
  • Shallow and SHA-256 git repositories are refused for now.
  • CI tests Linux and other Unix-like systems; Windows is not tested yet.
  • Milestones 0–4 are done. 5 is in progress: deltas, chunked large files, derived indexes, blame and the benchmark script are in. 6, the server, has a first version, BraidHub; its caches are planned, and so is 7: the daemon, the virtual file system and a WebAssembly core.
  • Versión 0.1: deja git como fuente de verdad, y no guardes nada solo en braid.
  • La velocidad y el tamaño frente a git están en «Medido frente a git», como ratios de una ejecución del script y con el commit medido: compruébalos antes de contar con la velocidad de braid.
  • BraidHub, que lleva braid a varias máquinas, es una primera versión: para todo lo que importe, ten un espejo en GitHub como fuente de verdad. Aún no hay daemon por máquina, cachés ni sistema de ficheros virtual.
  • Nunca se borra nada de un almacén; aún no hay recolección de basura.
  • El formato v1 está congelado. El almacenamiento y los protocolos aún pueden cambiar, y un braid antiguo rechaza un almacén más nuevo en vez de adivinar.
  • Las fusiones son textuales: dos cambios pueden fusionarse limpiamente y aun así romper la compilación.
  • log -- path y blame siguen los primeros padres y no siguen los renombrados.
  • Los clones superficiales y los repositorios SHA-256 de git se rechazan por ahora.
  • La integración continua prueba Linux y otros sistemas tipo Unix; Windows aún no se prueba.
  • Las fases 0 a 4 están terminadas. La 5 está en marcha: ya están los deltas, los ficheros grandes troceados, los índices derivados, blame y el script de benchmarks.
